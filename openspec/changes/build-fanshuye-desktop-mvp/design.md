## Context

番薯叶是面向开发团队的桌面任务态势工具。它用一棵番薯树表示开发组的活跃任务：叶子位置表达行动等级，叶片大小表达重要度，轮廓、填充和图标表达认领、工作流及阻塞状态；叶子本体不显示负责人头像，责任信息在悬停卡片和详情面板中以文字出现。

当前仓库是空白项目，没有既有代码或数据需要兼容。MVP 需要优先证明悬浮任务树、唯一主负责人、原子认领、人工状态更新和多端同步能够减少任务遗忘与重复开工。任务进度完全由人确认；Agent、Git 平台集成和 Neo4j 均为后期能力。

主要参与者包括开发团队成员、团队管理员和负责部署服务端的运维人员。首发桌面平台按 Windows 11 设计，架构保留移植其他桌面平台的边界，但不在本期承诺跨平台一致性。

## Goals / Non-Goals

**Goals:**

- 建立可安装的 Tauri 2 桌面客户端，提供托盘、边缘悬浮入口、速览任务树和标准详情窗口。
- 建立支持团队、任务、唯一负责人、协作人、人工工作流、阻塞、重要度、截止时间和完成定义的核心领域模型。
- 通过服务端原子命令防止同一任务被两名成员独立认领。
- 支持同一工作区内的 `BLOCKS` 前后依赖，并保证依赖关系始终为 DAG。
- 通过服务端事实源、乐观并发控制、幂等命令、实时通知和游标恢复实现可靠协作。
- 支持断网查看最近一次确认的数据，但不在首版接受离线修改。
- 为全部正式任务变化提供可追溯的追加式审计事件。
- 为后续 Git、Agent 建议和 Neo4j 图查询投影保留稳定但最小的扩展边界。

**Non-Goals:**

- 自动识别任务进度、百分比进度或 Agent 自动调度。
- GitHub、GitLab、文档、聊天或本地行为采集。
- Neo4j、向量数据库、Kafka、完整事件溯源或微服务拆分。
- 离线创建、离线编辑、outbox 或复杂冲突合并。
- 甘特图、Sprint 规划、工时核算、资源预测、自定义字段或自定义工作流。
- 任意关系图；MVP 只支持具有硬阻塞语义的 `BLOCKS`。
- 在叶片上显示头像、人名缩写或人员专属颜色。
- 同时交付 Windows、macOS 和 Linux 的生产体验。

## Decisions

### 1. 使用模块化单体和单一事实数据库

系统采用一个桌面客户端、一个 TypeScript 模块化单体服务端和一个 PostgreSQL 数据库：

```text
┌──────────────── Tauri 2 桌面客户端 ────────────────┐
│ overlay 悬浮窗口 │ main 详情窗口 │ TypeScript UI   │
│ 同步控制器       │ SQLite 缓存   │ 最小 Rust 适配层 │
└───────────────┬──────────────────────┬──────────────┘
                │ HTTPS REST           │ WSS
                ▼                      ▼
┌──────────── TypeScript 模块化单体服务端 ───────────┐
│ Identity │ Team │ Task │ Priority │ Dependency     │
│ Sync     │ Audit │ Notification                    │
└────────────────────────┬───────────────────────────┘
                         ▼
                    PostgreSQL
```

建议采用单仓库边界：

```text
apps/
  desktop/       Tauri、桌面窗口与应用界面
  server/        API、领域模块、同步与数据库访问

packages/
  contracts/     版本化 DTO、事件信封、错误码和运行时校验
  domain/        状态机、优先级和依赖规则
  ui/            任务树、叶片、卡片和详情组件
```

选择模块化单体是因为首版团队规模和部署复杂度不需要微服务。模块必须通过应用服务或领域接口协作，禁止跨模块直接修改表。未来 Agent 或图分析服务可通过版本化 API 和事件接入，而不要求现在承担分布式事务和消息队列运维。

替代方案是从一开始拆分任务、同步、图关系和 Agent 微服务；该方案会提前引入服务发现、消息可靠性和跨服务一致性，故不采用。

### 2. Tauri 负责原生边界，TypeScript UI 负责产品交互

Tauri Rust 层保持精简，仅负责：

- 单实例、窗口创建与定位。
- 系统托盘、全局快捷键、可选开机启动。
- 操作系统安全凭据存储。
- SQLite 缓存访问。
- 参数校验后的最小 IPC 命令。

TypeScript UI 负责业务界面与同步状态。首版使用两个窗口：

- `overlay`：透明、无边框、置顶的悬浮窗口；收起时是屏幕边缘小叶苗，短暂悬停后展开，点击后固定。
- `main`：普通窗口，承载全量列表、搜索、历史和复杂详情编辑。

任务树首版使用 SVG。直接展示约 12 至 16 片活跃叶子，其余聚合为叶簇。SVG 在该数量级下便于命中检测、键盘导航、无障碍语义和轻量动画；Canvas/WebGL 更适合更大规模，但会增加可访问性和测试成本，因此暂不采用。

悬浮窗口不得抢夺编辑器焦点。透明点击穿透、多屏恢复和 DPI 缩放封装为平台适配层；若 Windows 透明窗口在目标设备上不稳定，降级为固定侧边面板而不改变任务能力。

### 3. 任务事实与树布局完全分离

PostgreSQL 保存任务事实，客户端从任务字段派生树布局。不得保存权威叶片像素坐标。

主要实体：

```text
Workspace
  ├─ Membership
  └─ TaskTree
       ├─ Workstream
       └─ Task
            ├─ TaskCollaborator
            ├─ TaskDependency
            ├─ TaskExternalReference
            └─ TaskEvent
```

首版每个工作区自动创建一棵默认树和一个默认工作流分组，避免在 UI 中暴露复杂配置。实体全部使用稳定 UUID。`Task` 至少保存标题、说明、完成定义、唯一负责人、状态、人工阻塞、重要度、截止时间、版本和归档时间。

替代方案是把树结构或叶片坐标直接保存为任务数据；这会让分辨率、筛选和优先级变化影响业务事实，也妨碍列表视图和后续图依赖，因此不采用。

### 4. 将工作流、责任归属和阻塞拆成正交维度

正式状态机为：

```text
TODO ──StartTask──────▶ IN_PROGRESS
IN_PROGRESS ──────────▶ IN_REVIEW
IN_REVIEW ────────────▶ IN_PROGRESS
IN_PROGRESS/IN_REVIEW ─▶ DONE
任一非终态 ───────────▶ CANCELED
DONE/CANCELED ─────────▶ TODO  （ReopenTask）
```

`IN_REVIEW` 是可选阶段。`BLOCKED` 不是主状态：

```text
effectiveBlocked = manualBlocked OR hasIncompletePrerequisite
```

一个任务最多有一个主负责人，可以有多个协作人。无人负责的 `TODO` 任务执行 `StartTask` 时，在同一事务中完成认领和进入 `IN_PROGRESS`。暂停返回 `TODO` 但保留负责人；释放返回 `TODO` 并清空负责人。完成和取消任务退出活跃树，但继续保留历史。

所有状态转换都使用语义命令，服务端从认证会话推导操作者，客户端不能提交任意目标状态或自行声明操作者。默认权限为：管理员可处理所有团队任务；普通成员可创建任务、认领无人负责任务，并修改自己负责或参与的任务；转交他人、修改他人责任归属和团队管理操作需要当前负责人同意或管理员权限。

选择正交建模是为了避免“进行中且阻塞”“评审中且阻塞”等真实状态被迫映射成互斥枚举，也为后续 Agent 判断提供清晰目标。

### 5. 原子认领、乐观并发与幂等命令

所有修改使用语义化命令，例如：

```text
CreateTask             UpdateTaskDetails
StartTask              PauseTask              ReleaseTask
TransferOwner          AddCollaborator         RemoveCollaborator
BlockTask              UnblockTask
RequestReview          RequestChanges          CompleteTask
CancelTask             ReopenTask
AddDependency          RemoveDependency
```

每个命令携带客户端生成的 `commandId`；现有聚合的修改还携带 `expectedVersion`。服务端使用 `processed_commands` 去重，并在一个事务中完成权限检查、状态更新、聚合版本递增、团队事件序号分配和审计事件写入。

原子认领使用条件更新或行级锁，条件至少包含任务 ID、`owner IS NULL`、`status = TODO` 和预期版本。同时竞争时只允许一个事务成功；失败方收到最新负责人文字和任务版本，并可选择加入协作或请求接手。

替代方案是客户端先乐观展示认领成功再异步协调；这会在核心痛点上产生短暂双负责人和错误认知，因此关键命令必须等待服务端确认。

### 6. 使用可解释的三档行动等级和稳定排序

重要度保存为 1 至 5，树面映射为：1–2 小叶、3 中叶、4–5 大叶。行动等级保存派生结果和解释，不用不透明总分：

1. 逾期或 24 小时内截止的可执行任务至少为 `NOW`。
2. 7 个日历日内截止的可执行任务至少为 `NEXT`。
3. 重要度 4–5 可把 `LATER` 提升到 `NEXT`，但不得仅凭重要度进入 `NOW`。
4. 阻塞更高行动等级后续任务的前置任务最多提升一个档位。
5. 有原因和未来失效时间的人工覆盖最后应用，但不隐藏阻塞或逾期风险。

团队时区用于计算截止窗口。服务端输出行动等级和主要理由；客户端只负责布局。同档内使用明确人工顺序、截止时间、重要度和稳定任务 ID 形成确定排序。后台更新不在已展开会话中立即洗牌，只有跨档或成员主动刷新时进行安全重排。

替代方案是用复杂加权总分连续排序；它难以解释、容易造成树面抖动，也会让团队争论权重，因此首版不采用。

### 7. PostgreSQL 实现依赖 DAG，Neo4j 仅保留后期投影边界

首版仅支持：

```text
前置任务 A ──BLOCKS──▶ 后续任务 B
```

`task_dependencies` 保存工作区 ID、前置任务 ID、后续任务 ID、创建人和时间，并通过约束与事务保证：

- 不允许自依赖或重复边。
- 两端任务必须属于同一工作区。
- 新增关系不得形成直接或间接环。
- 删除或归档策略不得产生悬空边。

依赖模块暴露稳定端口：

```text
DependencyCommandPort
  addBlockingDependency()
  removeDependency()

DependencyQueryPort
  getPrerequisites()
  getDependents()
  isReachable()
  getImpactSubgraph()
```

当前端口全部由 PostgreSQL 实现。新增边时锁定工作区的图版本行，再使用递归 CTE 检查从后续任务到前置任务是否已经可达，防止两个并发请求分别通过检查后共同成环。遍历设置超时和最大节点数。

PostgreSQL 是任务和依赖的唯一写入事实源。只有当多层影响分析、关键路径或跨实体图查询经过测量成为瓶颈后，才考虑：

```text
PostgreSQL 状态与事件
          │
          ▼
异步图投影器
          │
          ▼
Neo4j 只读分析投影
```

禁止同步双写。Neo4j 即使加入也先只实现复杂查询端口，并返回投影水位；投影落后或不可用时回退 PostgreSQL 或明确提示陈旧。该方案避免两个数据库同时成为权威事实源。

### 8. REST 是可靠命令通道，WebSocket 是低延迟通知通道

读取接口提供一致性快照、游标后的增量事件和任务详情；写入接口提供语义命令。WebSocket 只向已授权工作区连接推送事务提交后的事件，不作为唯一恢复来源。

同步流程：

1. 首次登录下载团队快照和 `snapshotCursor`。
2. 客户端按团队单调序号应用实时事件。
3. 检测序号缺口或重连时请求游标后的增量。
4. 游标过期、事件版本未知或本地投影无法应用时重新下载快照。
5. 重复事件通过团队序号和任务聚合版本幂等忽略。

服务端在正常网络条件下目标是让核心任务变化于两秒内出现在其他在线客户端。顺序由每工作区事件序号保证；这是首批小型开发团队可接受的串行点，后续以事务等待指标决定是否分区。

### 9. SQLite 仅是可重建的确认数据缓存

桌面 SQLite 保存最近一次服务端确认的任务摘要、详情、协作人、依赖、成员显示名称、同步游标和快照时间。缓存与游标在一个 SQLite 事务中推进。

离线时：

- 允许查看缓存树、列表和详情。
- 明确显示离线状态及最后同步时间。
- 禁用认领、状态转换、依赖修改和任务编辑。
- 不创建 outbox，也不把本地操作显示为成功。

缓存损坏或模式不兼容时将其视为可丢弃投影并重新下载服务端快照。刷新令牌和第三方凭据存入操作系统安全凭据存储，不进入 SQLite。

替代方案是首版支持离线写入；这需要冲突合并、命令重放和更复杂的 UX，会分散对核心协作价值的验证，因此推迟。

### 10. 当前状态表是事实源，事件用于审计、同步和未来扩展

不采用完整事件溯源。`tasks` 等当前状态表提供简单可靠读取，`task_events` 以追加方式保存审计和同步事件。事件与状态变化在同一 PostgreSQL 事务中提交。

事件信封至少包含：

```text
eventId
workspaceId
workspaceSequence
aggregateType
aggregateId
aggregateVersion
eventType
schemaVersion
actorType       human | integration | agent | system
actorId
occurredAt
commandId
correlationId
causationId
payload
```

客户端不能自行声明 `actorType`；服务端根据认证主体确定来源。事件载荷只保存必要差异与业务理由，不复制访问令牌或不必要的个人数据。

为未来 Agent 只预留统一命令、版本化事件、稳定任务 ID、完成定义和通用外部引用。首版不创建 Agent 服务、证据管线、建议表或向量数据库。未来 Agent 应产生待确认建议；成员接受后仍由普通任务命令形成正式状态与审计。

### 11. 最小权限与桌面安全

- 所有生产 REST 和 WebSocket 流量使用 TLS。
- 每个命令、查询、快照、增量读取和实时订阅都做工作区成员与对象级授权。
- 首版账户使用经过验证的邮箱和密码登录；密码只以强密码哈希保存，刷新令牌可撤销并存入操作系统安全凭据管理器。
- 成员被移除或会话撤销后，服务端关闭相关实时连接。
- Tauri 使用严格 CSP、固定允许连接的服务端来源、禁止任意远程导航，并只开放必要 IPC。
- 用户输入按纯文本或受限 Markdown 渲染；外部链接只允许明确安全协议。
- 本地任务缓存位于应用私有目录；是否启用数据库级加密在试点威胁模型后决定，但凭据从第一版起不得进入缓存。
- 首版不采集键盘、截图、剪贴板、麦克风、私聊或本地代码内容。

### 12. 测试与可观测性按风险分层

- 领域单元测试覆盖完整状态转换矩阵、优先级规则和依赖规则。
- PostgreSQL 集成测试使用真实并发连接验证原子认领、幂等、事务回滚和并发成环防护。
- 同步集成测试覆盖重复事件、乱序、断线、游标缺口和快照恢复。
- 桌面测试覆盖 hover、固定、托盘、快捷键、焦点、多显示器、DPI、减少动画和隐私模式。
- 权限测试覆盖跨工作区直接对象引用和 WebSocket 订阅隔离。
- 性能基线至少使用 1,000 个任务、100 个活跃任务和多层依赖；树只渲染聚合后的可见节点。
- 生产指标至少包含命令延迟/失败率、版本冲突、认领冲突、WebSocket 在线连接、游标恢复、快照重建和依赖查询耗时。

## Risks / Trade-offs

- **透明悬浮窗在真实 Windows 设备、DPI 和多屏环境中可能不稳定。** → 先建立原生验证矩阵，并保留固定侧边面板降级方案。
- **树形隐喻在任务多时失去可读性。** → 限制直接叶片数量，保留叶簇、筛选、搜索和完整列表。
- **人工状态可能逐渐陈旧。** → 将五个高频状态操作放在一到两步内，显示最后更新时间；Agent 仍不进入 MVP。
- **派生优先级可能引发团队争议。** → 使用离散、可解释规则，展示理由，并允许带原因与期限的人工覆盖。
- **工作区级事件序号与依赖图写锁可能形成热点。** → 首批小团队可接受；监控等待时间，只在测量后优化粒度。
- **SQLite 只读策略牺牲离线编辑。** → 换取清晰一致性和较低实现风险；离线写入以后单独立项。
- **PostgreSQL 图遍历不如图数据库直观。** → 当前减少双库运维和一致性风险；通过端口与事件保留 Neo4j 只读投影路径。
- **状态表与审计事件存在数据重复。** → 换取简单查询、可靠审计和增量同步，避免完整事件溯源复杂度。
- **严格 `BLOCKS` 会阻止部分可提前开展的工作。** → 首版明确其为硬依赖；软关联以后引入不同关系类型，不弱化现有语义。

## Migration Plan

本项目是绿地项目，没有旧数据迁移。实施和上线顺序为：

1. 建立单仓库、桌面壳、服务端模块、共享契约和 CI。
2. 建立 PostgreSQL schema、迁移框架、本地开发环境和测试数据。
3. 实现身份、团队权限、任务状态机、语义命令、幂等、版本控制和审计。
4. 实现原子认领，并使用两个独立数据库连接验证并发竞争。
5. 实现依赖 DAG、工作区图写锁、递归查询和并发成环测试。
6. 实现快照、增量 API、WebSocket 推送和游标补齐。
7. 实现 SQLite 只读投影、缓存事务和损坏重建。
8. 实现悬浮入口、任务树、卡片、详情、列表和人工工作流。
9. 完成权限、CSP、凭据管理、安装包和 Windows 原生矩阵测试。
10. 以小型开发团队试点，观测同步恢复、认领冲突、依赖查询和悬浮窗稳定性。

服务端先于依赖其新能力的桌面客户端部署。API 使用版本前缀并至少保持一个桌面发布周期的向后兼容。数据库迁移采用向前兼容的 expand/contract 方式；生产回滚优先回退应用版本和关闭新能力，不自动执行破坏性 down migration。SQLite 是可重建缓存，客户端模式不兼容时删除投影并重新同步。
